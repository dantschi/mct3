Multi-Core: Thread-Level Parallelism

  • Zwei (oder mehr) Kerne auf einem Chip statt „doppelt so schneller“ Einzelkern
  • TLP: unabhängige Threads/Tasks parallel
  • Beispiel: UI/Media auf Kern 0, Hintergrundarbeit auf Kern 1
  • Oft bessere Energieeffizienz als ein extrem hoch getakteter Kern

Zweiter Arbeiter statt einen zu überhitzen — aber Kommunikation wird zum Problem.

Symmetric Multiprocessing (SMP)

  • SMP: alle Kerne gleichartig (symmetrisch)
  • Gemeinsamer Zugriff auf RAM und Peripherie
  • OS (Linux, FreeRTOS, …) kann Tasks migrieren
  • big.LITTLE u. Ä. hier ausgeblendet — Fokus SMP

Klassisches PC-/Phone-Modell: gleichberechtigte Kerne, Scheduler verteilt.

Architektur eines SMP-SoC

  • Pro Kern: privater L1 (I und D)
  • Geteilt: oft L2 und DRAM (Shared Memory)

Private L1 für Tempo — darunter treffen sich die Kerne. Dort lauert die Kohärenzfrage.

Die Leitfrage des Tages

  • Write-Back (Block 2): Writes oft nur im privaten L1 — RAM kann veraltet sein
  • Core 0 schreibt score = 10 in seinen L1
  • Core 1 will score lesen
  • Woher weiß Core 1, dass die Wahrheit im L1 von Core 0 liegt — nicht im alten RAM?

Eine CPU: Write-Back genial. Zwei CPUs: ohne Kohärenz zerbricht die Semantik.

Kohärenzverlust (Stale Data)

  • Private Write-Back-Caches können unterschiedliche Sichten auf dieselbe Adresse erzeugen
  • Kohärenz (pro Adresse): alle Kerne sehen eine einheitliche Reihenfolge der Writes
  • Ohne Hardware-Kohärenz: OS-Flags, Queues, Sync unbrauchbar

Kohärenz \(\neq\) volle Speicher-Konsistenz für Mehrwort-Operationen — dafür später Atomics/Locks.

Warum Software-Flush scheitert

  • Bei DMA: gezielte Cache-Maintenance vor/nach seltenen Transfers
  • Bei Multicore: tausende Shared-Variablen pro ms (Queues, Locks, …)
  • Manuelles Spülen nach jedem Write zerstört den Multicore-Gewinn
  • Braucht unsichtbare, schnelle Hardware-Kohärenz

Write-Through überall wäre korrekt, aber Bus und Energie würden kollabieren.

Bus Snooping

  • Klassisch: Cache-Controller lauschen am gemeinsamen Bus/Interconnect
  • Fremder Zugriff auf lokal Modified → eingreifen (Daten liefern / Invalidate)
  • Große Systeme oft directory-basiert statt reinem Broadcast-Snoop

Idee bleibt: Caches koordinieren die „Wahrheit“ einer Adresse — Implementierung variiert.

MESI-Protokoll

  • State Machine pro Cache-Line (typisch 64 Byte)
  • Zustände: Modified (M), Exclusive (E), Shared (S), Invalid (I)
  • Basis vieler kohärenter Multicore-Designs (Varianten: MOESI, …)

Konzept der vier Buchstaben zählt — nicht jede Transitionstabelle auswendig.

MESI: Zustandsübersicht

Die Pfeile sind die klausurrelevanten Übergänge. Merken Sie sich besonders: Write auf Shared braucht Invalidate; Read-Miss auf Modified liefert der Owner.

Zustand M (Modified)

  • Line lokal geändert — RAM veraltet
  • Exklusiv: keine andere gültige Kopie
  • Klassischer Write-Back-„Boss“-Zustand

Monopol auf die Wahrheit dieser Adresse.

Zustand E (Exclusive)

  • Sauber: Cache = RAM
  • Exklusiv: niemand sonst hat die Line
  • Write → oft still zu M, ohne Broadcast

Sauber und allein — Schreiben ohne Netzwerk-Meeting.

Zustand S (Shared)

  • Sauber, aber mehrere Kerne haben Kopien
  • Gut für paralleles Lesen
  • Vor lokalem Write: andere Kopien invalidieren

Read-only-Sharing effizient — Write braucht Kohärenzaktion.

Zustand I (Invalid)

  • Nach Reset oder Invalidate
  • Inhalt unbrauchbar → Miss beim Zugriff
  • Daten müssen neu geholt werden

Leerer Eimer — nicht verwenden.

MESI: Read-Miss

Core 0 liest x, lokal I:

  • Request auf dem Interconnect
  • Niemand hat x → Memory liefert, Core 0 oft → E
  • Anderer Kern hat x sauber (E/S) → beide → S
  • Anderer Kern hat x Modified → der Owner liefert (Write-Back/Intervention), Zustände typisch → S

Snooping/Directory entscheidet: allein, geteilt oder Owner-Supply bei Modified.

MESI: Write auf Shared

  • Core 0 und 1: x in S
  • Core 0: x = 5
  • Vor Write: Invalidate-Broadcast
  • Dann lokal schreiben, Zustand → M

Geteilte Ressource nie heimlich ändern.

Reaktion: Invalidate

  • Core 1 sieht Invalidate für x → lokal I
  • Späteres Lesen → Miss → frische Kopie (Wert 5) von Core 0 / Memory-Pfad

Konsistenz: erzwungenes Verwerfen, dann Nachladen der Wahrheit.

MESI-Beispiel: Zustandsfolge

Zwei Kerne, Variable x, Start beide Invalid:

Schritt Aktion Core 0 Core 1
1 Core 0 liest x E I
2 Core 1 liest x S S
3 Core 0 schreibt x=5 M I
4 Core 1 liest x S S
  • Schritt 3: Invalidate-Broadcast, dann lokal M
  • Schritt 4: Owner-Supply (Intervention) oder Memory-Pfad → beide S

Typische Klausurfrage: Tabelle ausfüllen. Üben Sie die Sequenz Read-Miss → Shared → Write → Invalidate → erneutes Lesen.

Overhead von MESI

  • Preis: Kohärenz-Traffic (Invalidate, Snoop)
  • Viele Kerne + häufige Shared-Writes → Interconnect belastet
  • Große Server: Ringe/Meshes statt einfachem Broadcast-Bus

Skalierung: Verwaltungslast kann Datenbandbreite fressen.

False Sharing

  • Core 0: temp1, Core 1: temp2 — logisch unabhängig
  • Liegen in derselben Cache-Line → Write invalidiert den Partner
  • Ping-Pong trotz verschiedener Variablen
  • Abhilfe: Alignment / Padding auf getrennte Lines

Hardware kennt 64-Byte-Blöcke, keine C-Namen.

Software: gemeinsamer Zähler

  • MESI: Caches kohärent (pro Adresse)
  • Semantik von zaehler++ (RMW) ist MESI egal
  • Beide Kerne: zaehler++ auf globalem int — Erwartung: \(+2\)

Einfachste Aufgabe — parallel gefährlich.

Anatomie von i++

In C wirkt atomar — in Assembler typisch RMW:

lw   t0, 0(s1)   # Read
addi t0, t0, 1   # Modify
sw   t0, 0(s1)   # Write
  • Drei Schritte — können sich zwischen Kernen überlappen

CPU addiert nicht „im RAM“ — immer Register-Umweg.

Race Condition

  1. Core 0 liest 0
  2. Core 1 liest 0 (Shared)
  3. Core 0 schreibt 1
  4. Core 1 schreibt ebenfalls 1 (seine lokale Rechnung)

Ergebnis oft 1 statt 2 — ein Update verloren.

Wettlauf: beide rechnen auf demselben Startwert.

Naive Software-Locks

/* ohne volatile: Compiler darf den Spin-Loop wegoptimieren */
while (lock == 1) { }
lock = 1;
zaehler++;
lock = 0;

Idee: Mutual Exclusion — aber Check und Set sind getrennt.

Schloss-Metapher stimmt logisch — atomar nicht. volatile verhindert Compiler-Optimierung des Spins, macht Check+Set aber nicht atomar.

Warum Software-Locks scheitern

  • lock == 0 lesen und lock = 1 setzen: zwei Ops
  • Beide Kerne sehen „frei“ → beide betreten den kritischen Abschnitt
  • Race auf dem Lock selbst — braucht Hardware-Atomics

Problem nur verschoben — Silizium muss RMW unteilbar machen.

RISC-V A-Extension

  • Atomic Instructions: unteilbares RMW für eine Adresse zwischen Harts (gemäß Spezifikation)
  • Grundlage für Multicore-OS und sichere Shared-Zähler
  • Zwei Familien: LR/SC und AMO
  • Hinweis: paralleles DMA auf dieselbe Adresse bleibt Software-Risiko

Ohne Atomics kein korrektes Multicore-OS auf Shared Memory. DMA braucht eigene Sync-Disziplin.

LR/SC

  • lr.w: lesen + Reservation/Monitor auf Adresse
  • sc.w: schreiben nur, wenn Reservation noch gültig
  • Sonst: Store fehlgeschlagen → Software wiederholt

Überwachungszaun um die Adresse zwischen Load und Store.

LR/SC: Erfolg

  • Core 0: lr.w → frei → sc.w erfolgreich
  • Lock exklusiv übernommen

Erfolgspfad: wie RMW, Monitor still.

LR/SC: Fehlschlag

  • Beide: lr.w nahezu gleichzeitig
  • Core 0: sc.w ok
  • Core 1: sc.w scheitert (Reservation gebrochen / Kohärenz)
  • Software von Core 1 wiederholt die Schleife

Zweiter Kern prallt ab — Zustand bleibt konsistent.

LR/SC: Spinlock in Assembler

acquire:
  lr.w   t0, (a0)      /* Lock-Adresse in a0 */
  bnez   t0, acquire   /* belegt? erneut versuchen */
  li     t1, 1
  sc.w   t2, t1, (a0)  /* t2=0 bei Erfolg */
  bnez   t2, acquire   /* Reservation gebrochen → Retry */
  /* kritischer Abschnitt */
release:
  sw     zero, 0(a0)   /* Lock freigeben */
  • sc.w liefert Status in t2: 0 = Erfolg, sonst Fehlschlag
  • Typisches Muster für Mutex/Spinlock auf RISC-V ohne AMO

Genau diese Retry-Schleife erwartet die Klausur: LR, Test, SC, bei Fehler zurück. Release oft als einfacher Store (ggf. mit fence).

AMO-Befehle

    1. B. amoadd.w: Add am Speicherpfad
  • RMW in Hardware „hinter der Tür“
  • Adresse kurz für andere Zugriffe geschützt

Ein Befehl statt explizitem LR/SC-Loop für einfache Ops.

C11: <stdatomic.h>

#include <stdatomic.h>

_Atomic int zaehler = 0;

void isr_oder_core1(void) {
    atomic_fetch_add(&zaehler, 1);
}
  • Compiler erzeugt LR/SC oder AMO — kein Inline-Asm nötig

Modernes C trifft RISC-V-A — Brücke Software/Hardware.

Atomics schützen Daten, nicht vor schlechter Lock-Ordnung.

Kohärenz = Wahrheit; Atomics = unteilbare Updates. Als Nächstes: Amdahl und Semesterfazit.

Amdahls Gesetz

  • Nicht alles ist parallelisierbar: serieller Anteil \(s\), paralleler Anteil \(p = 1 - s\)
  • Speedup bei \(N\) Kernen:

\[ S(N) = \frac{1}{s + \frac{p}{N}} \]

  • Grenze für \(N \to \infty\): \(S_{\max} = 1/s\)

Mehr Kerne helfen nur dem parallelen Anteil. 10 % seriell → maximal 10× Speedup — egal wie viele Kerne.

Amdahl: Zahlenbeispiel

  • Programm: 80 % parallel, 20 % seriell (\(s = 0{,}2\))
  • 4 Kerne: \(S(4) = 1 / (0{,}2 + 0{,}8/4) = 1 / 0{,}4 = 2{,}5\)
  • 100 Kerne: \(S(100) \approx 1 / (0{,}2 + 0{,}008) \approx 4{,}8\)
  • Trotz 100 Kernen weit unter 5× — der serielle Rest dominiert

Klausurtypisch: Einsetzen und interpretieren. Optimierung des seriellen Pfads lohnt oft mehr als „noch ein Kern“.
